# Attachment download contract

`client.downloadAttachment(peer, messageId, elementId, destination)` downloads an existing message element and returns `{file: destination}`. CLI: `download --config FILE --kind private|group --target ID --message-id ID --element-id ID --destination FILE`. The CLI resolves its destination relative to the invoking directory; SDK callers supply an absolute path.

The public and native-service boundaries capture a plain peer and primitive strings before IPC, UID resolution or filesystem/native work. IDs remain exact decimal strings (including leading zeroes); object coercions, inherited/accessor fields, relative paths and NUL-containing paths reject. Caller mutation during UID lookup cannot change the requested message, element, destination or peer. The internal native peer is separately captured before filesystem awaits.

The request uses one `downloadRichMedia` dispatch with a private staging path. The completion must report matching `msgId` and `msgElementId`. Known `fileErrCode` and `fileSrvErrCode` fields both require explicit zero: string `"0"` is declared by the fixed listener; numeric zero is retained as SDK compatibility policy. A nonzero string or finite numeric code is preserved; missing/malformed values reject with `invalid-result`. Accessor properties are never evaluated. An explicitly reported `chatType` must match the request; absence is tolerated without inventing conversation metadata. The callback does not establish a peer UID independently.

The [fixed primary invocation](https://github.com/NapNeko/NapCatQQ/blob/26d7533e0f5800fdff865ab2f2ad7692917e1076/packages/napcat-core/apis/file.ts#L242-L263) returns the completion's filePath; it does not guarantee that this equals the requested path. The [fixed listener definition](https://github.com/NapNeko/NapCatQQ/blob/26d7533e0f5800fdff865ab2f2ad7692917e1076/packages/napcat-core/listeners/NodeIKernelMsgListener.ts#L4-L25) declares both error fields and chatType. Exact newly fetched source SHA256: invocation file `419252ccac06a05689ba2c8070dee3e5ef12342f0246fc71c6e95bf805451f0e`; listener `b775a29002ffa32a55dbb6a13ab1d4c0de14cad8be06ac207e6d2cacf126c149`. These are source-contract facts, not actual native-account download evidence. Upstream implementation is not incorporated.

Accordingly, a validated completion can supply a different absolute native cache path. The SDK rejects malformed/NUL native paths, requires a regular file and exclusively copies it to the destination. Read/copy failures preserve filesystem codes with fixed public messages rather than exposing native cache paths. It removes only its own staging directory, retains the native cache file and never overwrites an existing destination, including one created during the transfer. Success confirms local publication only; this API currently does not verify content against message metadata hashes.

The existing 120-second event deadline and Session close terminate observation without replay. Closing before publication prevents subsequent publication; a filesystem copy already dispatched cannot be retrospectively cancelled. If close is observed after that copy completes, the result rejects but the copied file is retained; it is not deleted as a guessed rollback. Dispatched native download work itself is not cancelled. Unknown native operations are not retried and timeout/failure must not be interpreted as proof that the vendor transfer never occurred.

Synthetic service tests and actual temporary-file fixtures cover pending UID mutation, malformed preflight, completion failures/getters, cache-path copies, destination collisions, late native rejection and public/CLI dispatch. They do not establish a real QQ download, peer interoperability or signing authenticity. Account download acceptance requires a separately authorized batch; previously consumed login/read permissions are not reused.
